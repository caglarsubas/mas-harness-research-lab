## 1. Hypothesis (falsifiable)

H-30: the roadmap build's validators refuse every seeded inconsistency class of the register (dangling dependency; status against evidence state; score drift; a status change without an update entry; a stale snapshot digest) and the lab's added class (a stale reference: an unknown harness key, an unknown codebase id, a duplicate item id) on a scratch copy of the record, with the refusal naming the edited item or field, and refuse none of three benign control edits.

- Unit: one build of the work copy after exactly one edit of its `roadmap.json`; refused = the build process exits non-zero and its last stderr line starts with `roadmap.json:` (the validators' own form); caught (an attributed refusal) = refused and that line contains the edited item's id, the edited research entry's id or short name or file name, or the edited field's name (`dependsOn`, `evidenceState`, `benefit` or `B2`, `status`, `harnesses` or `H99`, `codebases` or the unknown codebase id, `id`, `sha256`), matched as whole tokens (not inside a longer word, where letters, digits, underscore and hyphen continue a word). A refusal that names none of these is recorded as an unattributed refusal and does not count as caught. A non-zero exit whose last stderr line does not start with `roadmap.json:` is a crash: for a seeded edit it is not caught; for a control it is a false positive, as is a control's refusal (any non-zero exit of a control counts). A warning with exit 0, including anything the architecture builder prints, is not a refusal.
- Seeded edits, 6 classes x 3 instances = 18, targets drawn with seed 20261105 from the items or entries that qualify:
  M1 dangling dependency: append an unknown id to an item's `dependsOn` (3 items).
  M2 status against evidence state: a DONE item's `evidenceState` set to PLANNED (3 items).
  M3 score drift: one benefit factor set to 7 (above the 1-5 scale); one set to 0 (below it); one factor key removed (3 items).
  M4 status change without an update entry: a READY item whose evidence state is already consistent with DONE (IMPLEMENTED or CONTRACT_ADOPTED, so that M2's contradiction is not created by the edit) has its status set to DONE with `updates` untouched (3 items).
  M5 stale reference (the lab's added class, not in the register): an unknown harness key added to an item's `harnesses`; an unknown codebase id in an item's `codebases`; an item appended as an exact duplicate of an existing one (duplicate id).
  M6 stale snapshot digest (the register's class): a research source's `sha256` cut to 63 characters (malformed); a seed paper's `sha256` replaced by another 64-character value while its file under the copied `research/papers/` is unchanged (stale against the file); a secondary paper's `sha256` replaced by another value (stale; that corpus keeps no file in the bridge).
- Controls, 3 benign edits that a correct validator must accept: a description extended by one sentence; a dated update entry appended; a title extended by a marker.
- Measures: per class, attributed refusals of 3 (and refusals of any kind, descriptive); recall = attributed seeded refusals / 18; false positives = controls refused / 3; precision = attributed seeded refusals / (all seeded refusals + control refusals); the first 120 characters of each refusal message (the validator's words), its attribution, and the wall time per build.
- Minimum effect of interest: a class is "caught" when at least one of its three instances has an attributed refusal and "covered" when all three have; the hypothesis says every class is covered, and the lab would act (propose a validator) only on a class the build does not catch at all.
- Gate, evaluated in this order (regions disjoint and exhaustive over attributed counts in 0..18 and control refusals in 0..3):
  first, the precondition: when the baseline build of the unmodified copy does not exit 0, the result is UNRESOLVED and nothing else is evaluated;
  PASS when all 18 seeded edits have attributed refusals and 0 controls are refused;
  FAIL when any class has 0 of 3 attributed refusals (a class the validators do not catch), or when at least 1 control is refused (a false positive);
  UNRESOLVED when every class has at least 1 attributed refusal but fewer than 18 in all, with 0 controls refused (partial coverage inside classes; the uncaught instances and any unattributed refusals are named).
- Expected outcome class, stated in advance: M4 is the class most likely to be uncaught, since a missing update entry is a process rule rather than a shape rule; M6's second instance can be caught only by a validator that compares the record's digest with the copied paper file, and its third instance (a secondary paper with no file in the bridge) cannot be caught by any file comparison, only by a shape check it is built to pass, so an all-18 PASS is probably unreachable; the lab expects FAIL through M4 and says so now.
- Confounds, named: the validators and the record share an author, so a caught class may reflect that author's habits rather than a general rule; three instances per class are few; the seeded edits are the lab's operationalisation of each class, and another operationalisation could be caught differently. A PASS says the named edits are refused, nothing about edits of other kinds.

## 4. What is PASS, FAIL, UNRESOLVED

As the gate in section 1. A FAIL or UNRESOLVED is recorded as the finding; no re-tuning of the edits, the classes or the gate under this id; a different operationalisation of a class is a new id that names this one.
