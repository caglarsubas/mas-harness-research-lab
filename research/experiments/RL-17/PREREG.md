## 1. Hypotheses (falsifiable)

H-27a (determinism; a claim of its own, not a stand-in for log replay, which is H-27d): two runs of the same class with the same seed produce byte-identical effect logs (every row, every field, serialised with sorted keys). Unit: one (class, seed) pair; 13 classes x 32 seeds = 416 pairs. Gate, in this order: the precondition first (the export's `classes.json` digest equals the digest the committed `results.json` names; otherwise UNRESOLVED for every claim); then FAIL when any pair differs; then UNRESOLVED when fewer than 39 pairs were produced (3 seeds per class); else PASS. Precedence for every claim below is the same: precondition, then FAIL, then UNRESOLVED, then PASS.

H-27b (the harness's own replay class): the committed class row of C3 (kind REPLAY_STALE, the campaign's replayed and stale messages) reproduces exactly on the pin: the lab's `ledger.class_row` output equals the committed row in `results.json` under RL-03's comparison (sorted-key JSON equality of the whole row). Gate: precondition; then FAIL when not equal; else PASS.

H-27c (duplicated and stale replays refused): after a run ends, replaying an accepted board operation (a) with the same operation id answers DUPLICATE_ID and changes no state, and (b) for the versioned operations (ACQUIRE, ASSIGN, RENEW, RELEASE, MERGE) with a fresh operation id and the original `expectedVersion` (the reordered case: the operation arrives after the version moved) answers STALE_VERSION, the version rule's own refusal, and changes no state. The board advances a record's version on every accepted versioned operation (five increment sites in `Board`), so the original acceptance always moves the version past the replay's `expectedVersion`; the driver nevertheless checks the record's current version before each stale replay and excludes, counting them, any attempt the version rule could not refuse. Unit: one replay attempt; the attempts are every BOARD_ANSWER row with answer ACCEPTED and no `retryOf` in the first run of every (class, seed) pair, replayed at the run's deadline tick through the same simulation's board (`Board.apply(deadline, op)`), the operation rebuilt from the row's fields (agent, to, item, op, opId, expectedVersion, claimOpId, workDigest, event). "Changes no state" = the logged `changed` field is false. Gate, in order: precondition; then FAIL when any duplicate or stale replay is ACCEPTED or any replay has `changed` true; then UNRESOLVED when no attempt could be posed, or the driver raised an exception on any attempt (an instrument gap, counted), or any duplicate answered something other than DUPLICATE_ID, or any stale replay was refused for a reason other than STALE_VERSION (a refusal that does not show the rule under test; counted and named); else PASS.

H-27d (log replay, the register's clause): the recorded operation sequence of a run (every BOARD_ANSWER row, in order, at its own tick, rebuilt into the board's operation form as in H-27c) replayed through the board of a fresh simulation of the same class and seed that was never run reproduces the claim and merge sequence exactly: for every versioned operation (ACQUIRE, ASSIGN, RENEW, RELEASE, MERGE) the replayed answer and the record version before it equal the recorded ones. Unit: one run (class, seed), the first run of each pair; 416 runs. The other operation kinds (MESSAGE, VERIFY) are replayed to drive the board and their agreement is reported by kind, descriptively. Gate, in order: precondition; then FAIL when the claim and merge sequence diverges in any run; then UNRESOLVED when the driver raised an exception or no run was replayed; else PASS. Expected outcome class, stated in advance: the board consults the simulation beyond its operation stream (the published `Board` reads the workers, the coordinator, the tasks, the artefacts and the task-pass state for verification and merge), so a FAIL at the first MERGE or VERIFY-dependent answer is the likely class; that finding is the D1 question itself (replay safety rests on durable state, not the log alone), and the report says so if it happens.

Overall verdict: PASS when H-27a, H-27b, H-27c and H-27d all PASS; FAIL when any FAILs; UNRESOLVED otherwise. Expected: PASS on H-27a, H-27b and H-27c (the harness was built with these refusals; RL-03 reproduced four class rows exactly) and FAIL on H-27d, so FAIL overall, with the divergence point named.
